# Provisioned stores

Any team member can create a WooCommerce store from the dashboard (**Stores** page). Each store
is a Helm release of the `urumi-store` chart in its own namespace, with its own WordPress,
MariaDB, volumes, Secrets, Ingress host and its own WooCommerce MCP server, which is registered
for the team automatically: its tools show up in chat and on `/v1/mcp` as `acme__list_orders`,
`acme__get_order`, … Deleting the store removes all of it. The original store (release `store`
in namespace `urumi`, `http://wordpress.local`) stays as it was; nothing here touches it.

The plan this implements, with the reasoning behind each choice, is
[multi-store-plan.md](multi-store-plan.md). This page describes what was built, how to verify
isolation, how recovery works, and the demo script. [Changes from the plan](#changes-from-the-plan)
lists where the implementation differs.

## How it fits together

```
dashboard ──► gateway  POST /v1/teams/{team}/stores      writes a row: status=requested (202)
                 │
           Postgres (gateway DB)  ◄── single source of truth (stores table)
                 │
       provisioner (gateway image, `gateway-provisioner`, own ServiceAccount, no Ingress)
         claims rows (FOR UPDATE SKIP LOCKED + lease), runs the steps ──► Kubernetes API + helm
                 │                                                       namespace store-acme
                 └── when ready: connector kind=store + team link + grant  ├─ store-wordpress, store-mariadb (PVCs)
                                                                           ├─ store-mcp (woocommerce-mcp image)
gateway ──(NetworkPolicy)──► store-mcp.store-acme.svc:8000/mcp ──► WordPress ├─ Secrets, Ingress acme.localtest.me
                                                                           └─ NetworkPolicies, ResourceQuota, LimitRange
```

| Piece | Where |
| --- | --- |
| `stores` table, API, caps, store connectors | `services/gateway/src/gateway/stores/`, migration `0009` |
| Provisioner (state machine, Helm, Postgres roles) | `services/gateway/src/gateway/provisioner/` |
| Store chart | `deploy/helm/urumi-store` (vendored Bitnami `wordpress` 34.1.3, `urumi-service` as `store-mcp`) |
| Store image | `deploy/images/store-wordpress` (`urumi/store-wordpress`: the core store's Bitnami image, pinned by digest, plus WooCommerce 11.2.1 and `store-setup.sh`) |
| Cluster rights, admission policy | `deploy/helm/urumi/templates/provisioner.yaml` |
| Dashboard | `apps/frontend/src/pages/stores.tsx`, `store-detail.tsx` |
| Isolation proof | `deploy/scripts/check-store-isolation.sh` |

### API

All routes need a user session (the dashboard's); API keys cannot manage stores.

| Route | What it does |
| --- | --- |
| `GET /v1/stores/settings` | Whether stores are enabled; per-user and platform caps; base domain |
| `GET /v1/teams/{team}/stores` | The team's stores with status, step, reason, URL, created time and creator |
| `POST /v1/teams/{team}/stores` `{name}` | 202 with the new store and its wp-admin password (once). Same `Idempotency-Key` header, or the same name in the team, returns the existing store (200, no password) |
| `GET /v1/teams/{team}/stores/{id}` | One store with its recent events (create, each step, failures, delete) |
| `DELETE /v1/teams/{team}/stores/{id}` | Creator or team admin. 202, status `deleting`; the store's connector is disabled in the same transaction, so its tools vanish at once. Repeating it is harmless |
| `POST /v1/teams/{team}/stores/{id}/retry` | Creator or team admin, failed stores only: provision again from the first step |

Rules enforced by the gateway:

* **Caps**: `STORES_MAX_PER_USER` (2) live stores per user and `STORES_MAX_TOTAL` (5 locally,
  10 in production) on the platform. The count and the insert run in one transaction holding a
  row lock on the user and a transaction-level advisory lock, so parallel requests cannot both
  pass (`test_per_user_cap_holds_under_parallel_requests` fires five at once; two succeed).
* **Slugs** come from the name: `[a-z][a-z0-9-]` up to 21 characters, no `_` (keeps the
  `<slug>__<tool>` split unambiguous, and `<slug>__update_order_status` under the agent's
  64-character tool-name limit). A slug is never reused, even after the store is deleted
  (`acme`, then `acme-2`), and never collides with a registry connector.
* **Store connectors** (`kind=store`, `owner_team_id` set) are visible to, and can be enabled
  for, the owning team only. The registry API refuses to edit or delete them ("delete the store
  instead"); enabling/disabling still works. Their URLs are generated by the platform, so like
  hosted servers they are exempt from the SSRF destination check.
* **Secrets never in the database**: the wp-admin password is generated by the gateway, returned
  once, and kept encrypted (Fernet, `UPSTREAM_CREDENTIAL_KEYS`) only until the provisioner has put
  it in the store's Secret; then the column is cleared.

### Provisioning steps

The provisioner runs a worker pool (`PROVISIONER_WORKERS=3`). A worker claims a row with
`SELECT ... FOR UPDATE SKIP LOCKED`, sets a lease (`lease_owner`, `lease_expires_at`, 60 s,
renewed every 15 s), and runs the store's next step; `step` records the last one that finished.
Every step is "make it so", so running one twice is harmless.

| Step | Action |
| --- | --- |
| `namespace` | Server-side apply `store-<slug>` with `urumi.io/managed-by=provisioner`, `urumi.io/store=<id>`, PSS `baseline` enforce / `restricted` warn; a RoleBinding to `urumi-store-manager`; ResourceQuota, LimitRange, default-deny NetworkPolicy. A namespace of that name that is not this store's is never adopted |
| `secrets` | `store-credentials` (WordPress admin, MariaDB root/user/replication passwords) and `store-mcp` (`ck_`/`cs_` REST key, `DB_URL`), created only if missing: a retry never rotates a password MariaDB was initialised with |
| `mcp-db` | Postgres role `store_<id>` owning schema `store_<id>`, `search_path` pinned on the role (see Isolation) |
| `release` | `helm upgrade --install store <chart> -n store-<slug>` with generated values; Helm never waits, so a call takes seconds. A `pending-*` release left by a killed process is uninstalled (first install) or rolled back first |
| `wait-ready` | Polls WordPress, MariaDB and the MCP server. `ImagePullBackOff`, `InvalidImageName`, config errors, a crash loop (5 restarts, with the last log line) or `exceeded quota` fail at once; otherwise the dashboard shows e.g. `Waiting for pods: WordPress 0/1, MariaDB 1/1, MCP server 1/1; last event: Readiness probe failed …` |
| `setup` | A second `helm upgrade` renders the `store-setup-<attempt>` Job (WP-CLI, `store-setup.sh`): activate WooCommerce, pretty permalinks, country/currency, Cash on delivery, no onboarding/coming-soon page, the REST key (`wc_api_hash(ck)` + `cs`), three demo products. A failed Job is retried with a new Job |
| `register` | One transaction: connector `kind=store` (`http://store-mcp.store-<slug>.svc.cluster.local:8000/mcp`), team link with all tools, a grant for the creator if they are a plain member, `status=ready`, audit event |

Dashboard status: requested / any step → **Provisioning** (with the running step), `ready` →
**Ready**, `failed` → **Failed** + reason, `deleting` → **Deleting**. Two stores in parallel are
Ready in about two minutes on a laptop.

Step failures (5xx from the API server, Helm errors, database errors, a failed setup Job) are
retried up to `PROVISIONER_MAX_ATTEMPTS` (3). RBAC/admission refusals (403/422) and the fatal pod
states above fail at once.

**Deadline**: `deadline_at = created_at + STORES_PROVISION_TIMEOUT_SECONDS` (900 s locally,
600 s in production). Past it the store fails with the step and the last thing it waited for
(`Timed out waiting for WordPress, MariaDB and the MCP server to become ready: Waiting for pods:
WordPress 0/1, …`), and its resources are removed. The row stays, with **Retry** and **Delete**.

**Delete**: connector rows (team links and grants cascade) → `helm uninstall` → delete the
namespace (PVCs, their local-path volumes and Secrets go with it) → wait until it is gone → drop
the store's schema and role → `status=deleted`, `deleted_at`. Each step tolerates "already
gone"; if Kubernetes is slow the row stays `deleting` and is picked up again.

**Drift**: every 5 minutes, a `ready` store whose namespace or Helm release has vanished becomes
`failed: Resources missing: namespace` and its connector is disabled; Retry rebuilds it.

## Isolation

### Network

Each store namespace denies everything in both directions (the provisioner's `default-deny`
exists before any pod; the chart adds its own), then allows only:

| Pod | Ingress from | Egress to |
| --- | --- | --- |
| WordPress | Traefik (`kube-system`), store-mcp and the setup Job in the same namespace | MariaDB (same namespace), DNS |
| MariaDB | WordPress and the setup Job (same namespace) | nothing |
| store-mcp | gateway pods in `urumi` only | WordPress (same namespace), DNS, public 5432 (the MCP database) |
| setup Job | nothing | WordPress, MariaDB (same namespace), DNS |

The gateway's own policy has one new egress rule: namespaces labelled
`urumi.io/managed-by=provisioner`, pods `app.kubernetes.io/name=store-mcp`, port 8000.

The store's MCP server reaches WordPress through its Service (`WC_CONNECT_URL`) while signing
for, and sending the `Host` of, the store's public URL (`WC_BASE_URL`), so no store traffic goes
through the ingress or leaves the cluster.

**Proof** (run it after creating two stores):

```bash
deploy/scripts/check-store-isolation.sh acme globex
```

```
== from store acme's MCP server
ok    ALLOWED  its own WordPress
ok    BLOCKED  store globex's WordPress
ok    BLOCKED  store globex's MariaDB
ok    BLOCKED  store globex's MCP server
ok    BLOCKED  the platform gateway
ok    BLOCKED  its own MariaDB (only WordPress may)
== from store acme's WordPress
ok    ALLOWED  its own MariaDB
ok    BLOCKED  store globex's MariaDB
ok    BLOCKED  store globex's WordPress
ok    BLOCKED  the internet
== from the platform
ok    ALLOWED  gateway -> store acme's MCP server
ok    BLOCKED  agent -> store acme's MCP server (only the gateway may)
ok    BLOCKED  core MCP server -> store acme's WordPress
all isolation checks passed
```

### Data

* **WordPress/MariaDB**: separate volumes and passwords per store.
* **MCP operations records** (idempotency keys and replayable tool results, i.e. order data) are
  the one thing outside the cluster (Neon). Each store's MCP server logs in as its own role
  `store_<id>`, which owns only schema `store_<id>` and has `search_path` set to it; it has no
  rights on other stores' schemas or on the core MCP server's `public.operations`
  (`test_postgres_role_and_schema_per_store` checks a cross-schema `SELECT` is refused). The
  admin DSN that may create roles (`PROVISIONER_MCP_ADMIN_DSN`) is only in
  `provisioner-secrets`.

### Kubernetes rights

| Who | Rights |
| --- | --- |
| provisioner, cluster-wide (`urumi-provisioner`) | namespaces; RoleBindings; `bind` on the one ClusterRole `urumi-store-manager` |
| provisioner, per store namespace | `urumi-store-manager` via the RoleBinding it creates there: what Helm creates (Secrets, Services, Deployments, StatefulSets, Jobs, PVCs, Ingresses, NetworkPolicies, PDBs, quota), read Pods, Events and Pod logs |
| gateway | unchanged: hosted servers in `urumi-mcp` only |

RBAC cannot filter by label, so the ValidatingAdmissionPolicy
`urumi-provisioner-managed-namespaces` refuses any namespace or RoleBinding change by the
provisioner's ServiceAccount outside namespaces labelled `urumi.io/managed-by=provisioner`.
A bug cannot delete `urumi`, relabel it, or bind itself in it. Check it without touching anything
real:

```bash
kubectl create namespace vap-test
kubectl delete namespace vap-test --as=system:serviceaccount:urumi:provisioner   # Forbidden by the policy
kubectl auth can-i get secrets -n urumi --as=system:serviceaccount:urumi:provisioner  # no
kubectl delete namespace vap-test
```

### Guardrails

* **ResourceQuota per store**: pods 6, requests.cpu 1, requests.memory 1536Mi, limits.memory
  3Gi, PVCs 2, requests.storage 6Gi, services 5, secrets 10. **LimitRange** defaults (250m /
  256Mi, requests 50m / 64Mi, max 1Gi) for containers that set nothing. A store in use measures
  about 500 MiB (WordPress ~240, MariaDB ~180, MCP ~80).
* **Caps** per user and platform (above), the **deadline**, and Pod Security `baseline`
  enforced, `restricted` warned, per store namespace.

## Recovery

* **Gateway restart**: nothing to do; it only writes rows.
* **Provisioner restart**: on SIGTERM a worker hands its store back (clears the lease), so the
  next provisioner resumes it immediately from the saved step; after a hard kill the lease
  expires within 60 s. A Helm call cut off mid-way leaves a `pending-install`/`pending-upgrade`
  release, which is uninstalled or rolled back before the step runs again
  (`test_a_restarted_provisioner_resumes_from_the_saved_step`).
* **Retry of create**: same `Idempotency-Key` (the dashboard sends one per dialog) or same name
  returns the existing store.

### Drill: kill the provisioner mid-install

```bash
# 1. Create a store (dashboard, or POST /v1/teams/{team}/stores) and wait until it shows
#    "Pods ready" (step `release` done).
kubectl -n store-initech get pods -w            # WordPress still starting

# 2. Kill the provisioner while it waits.
kubectl -n urumi delete pod -l app.kubernetes.io/name=provisioner

# 3. The new pod picks the store up from the saved step and finishes it:
kubectl -n urumi logs -f deploy/provisioner | grep -E 'taking over|step done|store ready'
```

The store's events show which provisioner did what (`details.worker`). From the run on
2026-10-21: steps `namespace` … `release` by `provisioner-…-nmvhq`, the pod killed at 00:20:55
while WordPress was starting, the new pod `provisioner-…-sfh7d` holding the lease four seconds
later, `wait-ready` and `setup` done by it, Ready at 00:22:03 (1 min 49 s after the request).

For a hard kill (no lease release) use `--grace-period=0 --force`; the store waits for the lease
to expire (up to 60 s) and then resumes the same way.

## Demo script

1. **Create two stores at once**: on the Stores page, create **Acme** and **Globex** (or two
   `POST`s in parallel). Both go Provisioning → Ready, the step shown as it runs. Copy each
   wp-admin password from the dialog.
2. **Place an order** on each storefront (`http://acme.localtest.me`, `http://globex.localtest.me`;
   Cash on delivery is enabled), or from WP-CLI:
   `kubectl -n store-acme exec deploy/store-wordpress -- wp --path=/opt/bitnami/wordpress wc shop_order list --user=admin`.
3. **Chat**: "Compare the orders in the Acme and Globex stores: how many does each have and what
   is the total value?" → the agent calls `acme__list_orders` and `globex__list_orders` and
   answers per store. The MCP servers page lists both with a **Store** badge.
4. **Isolation**: `deploy/scripts/check-store-isolation.sh acme globex`.
5. **Delete Globex** (type its name to confirm). Then show that it is gone everywhere:

   ```bash
   kubectl get ns | grep store-
   kubectl get pvc -A | grep store-
   helm list -A
   ```

   its tools are gone from the chat's tool list and the MCP servers page, and the audit log
   (Audit logs page, or the store's events) has `store.create`, the steps, `store.ready`,
   `store.delete`, `store.connector_removed`, `store.deleted`.
6. Optional: the recovery drill above with a third store.

MCP clients connected to `/v1/mcp` (Claude Code, Cursor) keep their old tool list after a store
is deleted until they reconnect: the gateway is stateless and does not send
`notifications/tools/list_changed`. Calls to the old tools then fail with `not_found`. The agent
and the dashboard update at once.

## Operating it

**Settings** (gateway and provisioner read the same `STORES_*`; keep them equal in the values):

| Setting | Local | Production |
| --- | --- | --- |
| `STORES_BASE_DOMAIN` | `localtest.me` (every name resolves to 127.0.0.1) | `shop.<domain>` with wildcard DNS `*.shop.<domain>` → the VPS |
| `STORES_TLS` / `PROVISIONER_TLS_CLUSTER_ISSUER` | off | on / `letsencrypt` (one certificate per store host, HTTP-01) |
| `STORES_MAX_PER_USER` / `STORES_MAX_TOTAL` | 2 / 5 | 2 / 10 |
| `STORES_PROVISION_TIMEOUT_SECONDS` | 900 | 600 |
| `PROVISIONER_STORE_IMAGE` / `PROVISIONER_MCP_IMAGE` | set to the commit by `deploy-local.sh` | set by `deploy-vps.sh` |

Offline, `*.localtest.me` does not resolve; use `dnsmasq` with `address=/localtest.me/127.0.0.1`.

**Secrets**: `provisioner-secrets/PROVISIONER_MCP_ADMIN_DSN`, created by
`create-local-secrets.sh` from `services/gateway/.env` if it has `PROVISIONER_MCP_ADMIN_DSN`,
otherwise from the WooCommerce MCP server's `DB_URL` (the Neon database owner, which may
`CREATE ROLE`). The provisioner also reads `DB_URL` and `UPSTREAM_CREDENTIAL_KEYS` from
`gateway-secrets`.

**Laptop memory**: plan on about 1 GB per store at peak (first boot), plus the platform and the
core store. Give Docker Desktop at least 8 GB for the core store plus two or three provisioned
ones.

**Backups**: `deploy/scripts/backup-store.sh` covers the core store only. Provisioned stores are
treated as disposable demo stores and are not backed up.

**Upgrades**: a new store image or MCP server image applies to stores created afterwards (and
to a store that is retried). Existing ready stores keep the release they were installed with.

### Troubleshooting

| Symptom | Check |
| --- | --- |
| Store stuck in Provisioning | The detail page shows the running step and what it waits for. `kubectl -n urumi logs deploy/provisioner`; `kubectl -n store-<slug> get pods,events` |
| Failed: `ImagePullBackOff` | The store or MCP image is not in the cluster: re-run `deploy-local.sh` (it imports `urumi/store-wordpress`), then Retry |
| Failed: setup job | `kubectl -n store-<slug> logs job/store-setup-<n>` (the reason has its last line) |
| Failed: `no database for store MCP servers` | `provisioner-secrets` is missing `PROVISIONER_MCP_ADMIN_DSN`; run `create-local-secrets.sh` |
| Failed: `Forbidden` / `denied by policy` | The RBAC or the admission policy refused a call; `kubectl get validatingadmissionpolicy`, `kubectl auth can-i … --as=system:serviceaccount:urumi:provisioner` |
| Store Ready but its tools fail with `upstream_unavailable` | The gateway's egress rule to `store-mcp` (values.yaml) and the store's `store-mcp` NetworkPolicy; `kubectl -n store-<slug> logs deploy/store-mcp` |
| Storefront does not open | `curl -I http://<slug>.localtest.me/`; Traefik must publish port 80 (k3d cluster config) |

## Changes from the plan

Things that turned out differently in practice, and what was done instead:

* **The MCP server migrates in an init container**, not a Helm `pre-install` hook
  (`migration.mode: initContainer` in `urumi-service`). A hook would make Helm wait for the
  migration (against Neon) inside the call, and its pod would start before the store's
  NetworkPolicies exist. The init container runs under the pod's own policy and Helm returns at
  once.
* **The setup Job is rendered by the chart**, enabled by a second `helm upgrade` with
  `setup.runId=<attempt>` once the pods are Ready, instead of the provisioner creating it through
  the Kubernetes API. All store objects stay in one chart; the run id makes each attempt a new
  Job (Job specs are immutable) and Helm removes the previous one.
* **The setup Job does not mount the WordPress volume**: WP-CLI writes its own `wp-config.php`
  from the database environment and uses the plugin baked into the image. No RWO volume sharing
  between pods, no node pinning.
* **No probe from the provisioner after `register`**: only gateway pods may reach a store's MCP
  server, by design. The MCP pod's readiness (it checks its database) and the setup Job (it
  installs the REST key) are the checks; the gateway's connector status shows reachability.
* **No separate leader lock**: per-row leases with `SKIP LOCKED` already make a second
  provisioner replica safe (it would just process other rows); the drift check is idempotent.
  The chart runs one replica with the `Recreate` strategy.
* **The platform-wide cap** uses a transaction-level advisory lock in addition to the row lock
  on the user: the user lock alone serializes one user's requests, not two users'.
* **`kind` is shown to every user** in connector listings (it was platform-admin only), so the
  dashboard can put a Store badge on store connectors.
* **Helm 4** (4.3.0, the version in use locally) is pinned in the image, checksum-verified.
  `deploy-local.sh` and `deploy-vps.sh` now run `helm dependency update` (file:// charts only),
  because the umbrella's `Chart.lock` is not committed and went out of sync with the new
  `provisioner` dependency.
* **Production signing**: a store's MCP server always signs for `http://<host>` and connects in
  plain HTTP to the in-cluster Service, also when the storefront is HTTPS. `APP_ENV=production`
  now accepts plain HTTP only when `WC_CONNECT_URL` is a `*.svc`/`*.svc.cluster.local` Service.
* **Tool descriptions** read `[Acme] [Store: Acme] List orders …` on `/v1/mcp`: the gateway's
  aggregator prefixes every server's display name, and the store's MCP server adds its own label
  (useful for clients that connect to it directly). Harmless; left as is.
* **Team deletion**: `stores.team_id` is `RESTRICT` as planned, but the gateway has no team
  deletion endpoint today, so nothing in the dashboard needs to explain it yet.
